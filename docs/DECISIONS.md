# Decisions log

Choices made while implementing `crm-platform-build-spec.md`, including every `[DECIDE]` item and any deviation from the spec. Newest at the bottom.

## Phase 0

1. **Next.js 16 rather than 15.** Spec says "15+". Next 16 renames `middleware.ts` to `proxy.ts` (Node runtime by default); the tenant rewrite lives in `src/proxy.ts`.
2. **Prisma pinned to 7.10.0.** The npm `latest` tag pointed at an 8.0 release candidate; 7.x is the current stable. Prisma 7 requires `prisma.config.ts`, the `prisma-client` generator with an explicit `output` (`src/generated/prisma`, git-ignored, regenerated by `postinstall`), and a driver adapter (`@prisma/adapter-pg`).
3. **Tenant isolation via a Prisma client extension** (spec §4 `[DECIDE]`). Every top-level operation on every tenant-scoped model gets `AND: [{ tenantId }]` appended; creates get `tenantId` forced. AND semantics were chosen over overriding the caller's filter so a query that names another tenant matches nothing rather than being silently redirected. The scoped-model list is explicit (`TENANT_SCOPED_MODELS`) because Prisma 7's generated client exposes no runtime DMMF; a unit test parses the schema and fails if the list drifts.
4. **`tenantId` on every child table too** (OrderItem, CartItem, ProductImage, ProductVariant, Address, OrderStatusEvent, Payment), not just aggregates. Slightly denormalised, but it lets the extension scope every model uniformly and avoids the "child table reachable without a tenant filter" hole.
5. **Customer accounts are separate per tenant** (spec §5 `[DECIDE]`). `UserRole.CUSTOMER` was added to the enum; a `User` always belongs to exactly one tenant except super admins. Same email in two stores = two accounts.
6. **Product variants are in the v1 schema** (spec §6, confirmed by the owner). `Product.hasVariants` flags whether stock is tracked on the product or on its `ProductVariant` rows; both carry SKUs unique per tenant.
7. **Money as integer minor units; tax in basis points; flat shipping per tenant** (confirmed by the owner). `Tenant.shippingFlatRate` and `Tenant.taxRateBps` drive checkout totals via pure helpers in `src/lib/money`. Currency, country and locale are per-tenant settings with USD/US/en-US as seed defaults until the first client's region is chosen.
8. **Order status transitions** (spec §6, flagged deviation): the enum is used exactly as specified. Transition rules allow `DELIVERED → REFUNDED` so post-delivery returns can be recorded; everything else follows the spec (no backwards moves, CANCELLED/REFUNDED terminal, SHIPPED cannot be cancelled, only refunded).
9. **Per-tenant sequential order numbers.** `Order.orderNumber` is unique per tenant and assigned from `Tenant.orderSequence` with an atomic increment, giving customers a short ID for guest tracking (spec §7.5).
10. **Auth.js: JWT sessions, host-only cookies, DB re-verification.** Credentials provider requires JWT strategy. Cookies carry no `Domain` attribute, so sessions are per subdomain. Guards re-read the user row on every request rather than trusting token claims (spec §5/§9 "re-checked per request"). Passwords use `bcryptjs` cost 12 — Auth.js itself does not hash. Login rate limiting is inside `authorize` so the built-in callback endpoint is covered too; the v1 store is in-memory (per instance), with an interface ready for Upstash/Redis.
11. **Route layout.** `app/(root)` serves the apex (landing + `/platform` super-admin); `app/[tenant]` serves subdomains via proxy rewrite, with `(storefront)` and `admin` beneath it. Store admin therefore lives at `<slug>.<root>/admin`, which keeps its cookies isolated from other tenants. Login pages sit in `(auth)` route groups outside the guarded `(dashboard)` layouts to avoid redirect loops.
12. **Hand-written SQL in the initial migration.** A partial unique index on `User(email) WHERE tenantId IS NULL` (Prisma can't express it; Postgres treats NULLs as distinct in the composite unique) and CHECK constraints on money/quantity columns. Verified that `prisma migrate dev` reports no drift.
13. **`.env.test` is committed.** It holds only the local test-database URL and a dummy secret, and CI relies on it. All other `.env*` files are ignored.
14. **Deferred to later phases / fast-follow:** CSV bulk product upload (spec §7.1 `[DECIDE]` → fast-follow), OAuth providers, custom domains (v2 extension point noted in `resolve.ts`), Row Level Security. Third-party providers (Stripe, Resend, Vercel Blob, hosted Postgres) are reserved as env vars and chosen when the product goes live.
15. **Local database is Docker Postgres 17** (owner's choice); `docker-compose.yml` creates both `zy_commerce` and `zy_commerce_test`.

## Going live (2026-09-04)

16. **Hosted database is Supabase; app on Vercel** (owner's choice). Runtime uses the pooled connection, the Prisma CLI uses the direct/session connection. `src/lib/db/connection.ts` resolves `DATABASE_URL`/`DIRECT_URL` and also the `POSTGRES_*` names the Vercel ↔ Supabase integration injects, so no manual mapping is needed.
17. **TLS policy for hosted Postgres.** node-postgres treats `sslmode=require` as full verification (and warns); Supabase URLs mean the libpq sense. `buildPoolSettings` maps require/prefer/no-verify → encrypted without verification, `verify-full` → verified, and encrypts by default for any non-local host.
18. **Migrations and seed run inside the Vercel production build** (`scripts/vercel-build.sh`), never for previews. The seed refuses to invent passwords on Vercel/production: accounts are created only when `SEED_*_PASSWORD` is set, so credentials never appear in build logs.
19. **Tenant host aliases** (`TENANT_HOST_ALIASES`). `*.vercel.app` cannot nest subdomains, so the demo store is served from its own vercel.app alias. The same mechanism is the v1 form of per-tenant custom domains; v2 moves it to a `Tenant.customDomain` column.
20. **Vercel project `zy-commerce` (team kzy02), functions in `sin1` (Singapore), Supabase in `ap-southeast-1`.** The owner is in the UTC+8 region and the first demo tenant is configured for MYR/MY, so the app and database sit next to each other in Singapore. The demo tenant is served from the alias `zy-commerce-demo.vercel.app` via `TENANT_HOST_ALIASES`; the platform root is `zy-commerce.vercel.app`.
21. **Database URLs are stripped of `sslmode`/`ssl*` params before reaching node-postgres.** pg merges the parsed URL over the explicit config, so Supabase's `sslmode=require` silently re-enabled certificate verification and the first production seed failed on Supabase's self-signed chain. `buildPoolSettings()` now removes those params textually and is the single source of truth for TLS. The Prisma CLI (migrate) handles TLS itself and was unaffected.
22. **Production is live** (2026-09-06): https://zy-commerce.vercel.app and https://zy-commerce-demo.vercel.app. Super-admin and demo-admin passwords live only in the Vercel project's environment variables (`SEED_*_PASSWORD`); a self-service password change is Phase 5 work.

## Demo catalogue & product assistant (2026-09-06)

23. **The demo tenant is "Selkirk Demo" with Selkirk Sport's full public catalogue** (192 products, 2,911 variants) for the owner's freelance proposals. Data comes from Selkirk's public Shopify feed plus each product page's `#tech-specs` block; only factual data (names, options, prices, specs, image URLs) is used, descriptions are generated from those facts, and images are hot-linked from Selkirk's CDN rather than copied. USD prices are converted to MYR at a fixed recorded rate. A real client would supply their own content and media.
24. **Structured specs live on `Product.specs` (JSON) and per-variant in `ProductVariant.attributes`.** Spec keys are normalised to Title Case at import so facets group correctly. This is the substrate the assistant reasons over and what future admin forms will populate (with LLM extraction from free text as a fallback).
25. **Assistant = a tool loop, not RAG embeddings.** With catalogues of hundreds to a few thousand products, keyword search + spec matching via Prisma is enough and stays tenant-scoped by construction; embeddings can be added later as another tool. The model finishes each turn with a `respond` tool call so the reply is structured (answer, quick-reply suggestions, product SKUs).
26. **Seed speed for Vercel builds:** the catalogue import stores a SHA-1 fingerprint on the tenant and is skipped when unchanged; otherwise products are processed 8 at a time with bulk inserts.

## Switched the assistant to DeepSeek (2026-09-06)

27. **Model provider is DeepSeek, on the store owner's own API key — not Claude via Vercel AI Gateway.** The owner wants zero cost on this project's own accounts while the platform is unproven: the gateway route needed a card on the Vercel team before it would serve any request, even free-tier ones. DeepSeek needs nothing from Vercel or Anthropic — the app talks to `https://api.deepseek.com` directly with `DEEPSEEK_API_KEY`, and every dollar of usage bills to whichever DeepSeek account owns that key, at DeepSeek's own (much lower) per-token rates. Hosting (Vercel Hobby) and the database (Supabase free tier) were already $0; this removes the last piece with a cost path.
28. **Implementation is the official `openai` SDK against DeepSeek's OpenAI-compatible endpoint**, not the Anthropic SDK against DeepSeek's newer (and, per DeepSeek's own docs, only partially verified) Anthropic-compatible endpoint. Tool definitions moved from Anthropic's `input_schema` shape to OpenAI's `{type:"function", function:{name, description, parameters}}`; the loop reads `choices[0].message.tool_calls` and appends `role:"tool"` results keyed by `tool_call_id`, per DeepSeek's [tool-calling guide](https://api-docs.deepseek.com/guides/tool_calls). Structured-output extraction (`extract-specs.ts`) uses DeepSeek's plain `response_format:{type:"json_object"}` JSON mode plus Zod validation, since DeepSeek does not document a strict schema-enforced structured-outputs mode the way Anthropic's beta does.
29. **Default model is `deepseek-v4-flash`**, the cheapest current DeepSeek model that still supports tool calling and JSON mode (context 1M, ~$0.22–0.44/1M input on a cache miss, ~$0.66–1.32/1M output, roughly a tenth of Claude Opus 5's price) — `AI_MODEL=deepseek-v4-pro` opts into the pricier, higher-quality model. No Vercel OIDC token, no `@anthropic-ai/sdk`, no `@vercel/oidc` dependency remain in the assistant code path.
30. **DeepSeek's "thinking" is explicitly disabled on every assistant call** (`thinking: {type: "disabled"}`). Measured against the real API: a trivial one-line reply used 90 prompt + 36 completion tokens with thinking on (32 of those completion tokens pure hidden reasoning) versus 11 + 3 with it off — roughly a tenth of the tokens and under half the latency (702ms vs 1657ms), with tool calling equally functional both ways. For this assistant's short, tool-grounded turns the reasoning overhead bought nothing; the resulting bug (decision 31) was fixed by correcting the tool and prompt, not by re-enabling thinking.
31. **Category filter in `search_products` matches slug or name, case-insensitively** — found via a live test against the real 192-product catalogue, where the model consistently passed the category *display name* ("Paddles") shown in the system prompt's overview instead of the slug ("paddles") the tool expected, exhausting every one of the 6 tool-call rounds on empty results. The catalogue overview now also states each category's slug explicitly. A live re-test with the same question resolved in 3 rounds with a grounded, specific recommendation, at roughly $0.003 for the whole exchange (~13k input tokens, most of it cache hits, ~700 output).

## Second demo store and the off-topic guard (2026-09-06)

32. **A second demo tenant, "Nike Demo", carries 104 Nike basketball products** (44 shoes, 21 jerseys, 14 shorts, 12 hoodies/jackets, 8 socks, 4 basketballs, 1 accessory) with 1,480 size variants. It exists to prove the platform is genuinely multi-tenant and genuinely product-type agnostic: the two stores run the same code with different catalogues, currencies (MYR vs USD), branding and assistants, and neither can see the other's data. `prisma/seed.ts` now iterates a `DEMO_STORES` list instead of hard-coding one tenant.
33. **Nike has no public product feed, so `scripts/import-nike-catalog.ts` reads the JSON nike.com embeds in its own pages** (`__NEXT_DATA__`): the category/search wall for the listing, then each product page for specifications, sizes, colourways and images. As with the Shopify importer, only factual data is taken (names, style codes, prices, colours, sizes, materials, Nike technology names, taxonomy, image URLs) — Nike's narrative marketing copy is never reproduced, descriptions are generated from the extracted facts, and images are referenced on Nike's CDN rather than copied. One product per model (Nike lists every colourway separately); size becomes the variant axis.
34. **Off-topic questions are rejected in code, before the model, so they cost nothing** (`src/lib/ai/topic-guard.ts`). The owner's requirement was explicit: no tokens on unrelated questions. A message passes if it names something in the catalogue (vocabulary built per request from category names/slugs, brands, product names, spec keys and values), carries a standalone shopping intent ("cheapest", "do you ship", "help me choose", plus common Malay/Chinese equivalents), is a greeting, or is a short follow-up in an existing conversation. A deny list of clear non-commerce intents (content generation, trivia, weather, maths, homework, finance, medical, prompt injection) takes precedence, so "write me a poem about shoes" is blocked despite naming a product. Everything else gets the fixed reply plus the store's sample questions.
35. **The guard is deliberately biased towards letting borderline questions through.** A wrongly blocked customer sees a broken assistant; a wrongly admitted question costs a fraction of a cent and the system prompt still keeps the model on the catalogue. Starter chips are generated from the same shared helper the guard is tested against, so a customer can never be told their own suggested question is off-topic.

## Split into a monorepo: product and showcase (2026-09-07)

36. **The repository is now a pnpm workspace with two projects**, because the sellable thing is the assistant, not the shop. `packages/catalog-concierge` is the product; `apps/zy-commerce` became a consumer of it and exists to demonstrate it on real catalogues. The old layout made the assistant look like a feature of one e-commerce app, which is the opposite of the intended positioning.
37. **The dependency was inverted via a two-method `CatalogAdapter`.** Previously the assistant's tools queried Prisma directly and knew about tenants. Now the package defines `listCatalogue()` and `getProduct()`, and the app implements them in `src/lib/ai/prisma-adapter.ts` over its tenant-scoped client. The package has no database driver, no ORM and no knowledge of tenancy; tenant isolation still holds because the adapter is built from an already-scoped client, which the integration test asserts directly.
38. **Search, ranking, category counts and product cards moved into the package**, computed from a single catalogue snapshot taken once per message. That means one read per message instead of one per tool call, ranking identical to what the store map saw, and an integration surface small enough that a new business implements two functions. The cost is an in-memory scan, comfortable into the low thousands of products and documented as the scale ceiling.
39. **The widget lost its dependencies on the host.** It no longer imports the app's design system or its Server Action; it takes an `onSend` transport and an optional `renderProductLink`, and styles itself with Tailwind utility classes plus the CSS variables most Tailwind projects already define. The app mounts it through a short wrapper component.
40. **Terminology changed from SKU to `ref`** inside the package, since a product reference need not be a SKU in another business's data model. The app maps its SKUs onto it.
41. **Package tests run with no infrastructure at all** — an in-memory adapter and a fake model client — which is faster and is the honest way to prove the package stands alone. Database-backed assertions stayed in the app, rewritten as adapter tests.
42. **Next.js needed two monorepo adjustments**: `transpilePackages` for the workspace package, which ships TypeScript source rather than a build step, and a Turbopack `root` pointing at the repository root so it resolves the hoisted lockfile and dependencies. The `.gitignore` patterns for generated and build output also had to be re-anchored with `**/`, since paths written when the app was the repository root silently stopped matching and would have committed the generated Prisma client.
43. **Tailwind must be told to scan the package** (`@source` in `globals.css`). Moving the widget into `packages/` silently broke its styling: Tailwind v4 generates only the classes it can see and does not scan dependencies, so every class used *only* by the widget — its fixed positioning, panel sizing, bubble corners, status dot — stopped being emitted. The panel still rendered, which is why a code review missed it; it just appeared unstyled in the top-left. Verified by grepping the built stylesheet for `.right-4` before and after. Documented in the package README as a required integration step, since every future host hits it.

## Pre-launch audit: closing the gaps before promoting the demos (2026-09-08)

43. **Conversation history is read from the database, never from the browser.** The storefront Server Action is a public HTTP endpoint, so the `history` the widget sent with each message was attacker-controlled: forged `assistant` turns entered the model's context as if the assistant had written them, and the Zod schema permitted 24 turns × 4000 characters — roughly 24k tokens of attacker text, resent on every one of up to seven tool rounds, billed to our own DeepSeek key. History is now reconstructed from the `ChatConversation` row keyed by the httpOnly session cookie (`src/lib/ai/chat-history.ts`); the field is still accepted so the widget's transport contract is unchanged, and ignored. The same read serves the logging write, so a turn costs one SELECT instead of two.

44. **The off-topic guard no longer treats "short" as "on-topic".** Rule 5 admitted any message of ≤6 tokens once a thread existed, which made the zero-token promise hold only for a customer's first message. Measured against the live Nike vocabulary, 11 of 14 off-topic probes reached the model; "give me a haiku" was answered with "I'd be happy to!" on the second turn of a real conversation. A short message now needs a reason beyond brevity: it points back at what is on screen (`REFERENTIAL_WORDS`, an ordinal or a number), it is a bare question word in a two-token message, or the assistant's own last turn ended in a question (`awaitingAnswer`) — which is the case that matters, because the assistant asks one clarifying question at a time and the answer is often a word no catalogue contains ("casually", "wide feet"). Same probe set afterwards: 2 of 12 reach the model, 0 of 15 genuine follow-ups and clarifying answers are wrongly blocked.

45. **A quick-reply chip can never be judged off-topic.** Tightening rule 5 broke `"Control and feel"` — a chip the assistant itself offers, which names nothing in the catalogue and points at nothing. Rather than loosen the rule, `ConversationTurn` gained an optional `suggestions` array and the guard admits a message matching a chip offered on the previous turn. The README claimed this guarantee before; now it is enforced.

46. **A bare number is an answer, not arithmetic.** The homework pattern `^[\d\s+\-*/().]+$` blocked `"300"` and `"10.5"` — a budget and a shoe size, the two most likely replies to the assistant's own clarifying question. It now requires an operator.

47. **Nothing is search-indexed, and every storefront says it is a demonstration.** The demos carry real brand names, product names and hotlinked CDN photography; ranking for those brands is what turns a clearly-labelled portfolio piece into something a trademark owner must act on. `app/robots.ts` disallows all crawling, the root layout sets `robots: { index: false }`, the footer states what the store is and is not, and the "Add to cart — coming in Phase 3" button became "Demo store — not for sale". That last change also removes the half-built read a prospective client would otherwise get: selling someone else's products was never the thing being demonstrated.

48. **Link previews are generated, and the image URL is pinned by hand.** Every share of these demos happens on Facebook or WhatsApp, and the pages had no OpenGraph tags at all. `next/og` renders a typographic preview — no product photography, because a link preview is exactly where provenance is lost. The URL is set explicitly in the tenant layout: left to the file convention, Next builds it from the matched route and emits `/{slug}/opengraph-image`, but the slug is internal, added by `src/proxy.ts`, so a crawler fetching that path gets it prefixed a second time and 404s. Verified against both tenant hosts.

49. **Security headers ship with the app.** CSP, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` and COOP, in `next.config.ts`. `script-src` still needs `'unsafe-inline'` because Next streams RSC payloads through inline scripts; the nonce-based upgrade needs a per-request nonce in `proxy.ts` and is deferred, but `frame-ancestors`, `object-src`, `base-uri` and `form-action` shut down clickjacking, plugin embedding, base-tag injection and cross-origin form posts regardless. Verified against a production build in a real browser: no console errors, images still load.

50. **The package is now something a client can actually install.** `exports` pointed at raw `.ts` and `build` was `tsc --noEmit`, so there was no artifact — the "two methods to integrate" pitch could not be honoured. It now emits JavaScript and declarations to `dist`, and `publishConfig` swaps those in at pack time while the workspace keeps consuming source with no build step. TypeScript emits bundler-style extensionless imports, which Node's ESM resolver will not follow, so a post-build pass writes the `.js` extensions into `dist` rather than polluting the source. Verified by packing the tarball, installing it into a bare Node project and importing it.

51. **The `.gitignore` negations were dead.** A trailing `.env*` sat below `!.env.example` and `!.env.test`, and the last match wins, so both negations did nothing. Harmless today because the files were already tracked, and silently wrong for the next one added.

## Store logo upload (2026-09-12)

52. **Logos are stored in Vercel Blob, as spec §3 fixes.** A public store, `zy-commerce-media`, was created in `sin1` beside the functions and connected to the project for Production, Preview and Development. The team's plan was checked first through the Vercel API (`billing.plan: "hobby"`), because Vercel's documentation guarantees Hobby users "will not pay for any additional usage" — Blob pauses at the free limit instead of billing. Public rather than private because a logo is shown to every visitor; a private store would route each image through a Function for no benefit.

53. **Uploads go through a Server Action, not a client-direct upload.** The file is at most 1 MB, so a server upload keeps authorisation in one place (`assertStoreAdmin()` on every call) with no client token to mint or scope. Server Actions cap request bodies at 1 MB by default, which a 1 MB file plus multipart overhead exceeds, so `experimental.serverActions.bodySizeLimit` is 2 MB. The form also checks size before submitting, because a request over the limit is rejected before the action can explain why.

54. **A file is identified by its bytes, never by its name or reported type.** PNG, JPEG and WebP signatures are checked on the server and the stored content type comes from that check, so a renamed file cannot choose its own. SVG is refused outright: it can carry script, and a public store serves it to anyone who opens its URL.

55. **The order of operations is validate → upload → save → delete the old file.** If storage fails, the current logo is untouched; if saving fails, the file just uploaded is deleted again; the previous logo is removed last and best effort, since a leftover file costs kilobytes while deleting first would leave the storefront pointing at nothing. Every upload gets a new URL via the SDK's random suffix, so no browser or CDN can keep serving a replaced logo.

56. **Only a logo the store itself uploaded is ever deleted.** `logoUrl` is just a column — seeded, or set by hand — so `isTenantLogoBlob` requires an https URL on a public Blob host *and* a path under `tenants/{this tenant's id}/`. A seeded image, another site's URL or another store's file is left alone; the integration tests assert each case.

57. **Tenant isolation is inherited, not re-implemented.** The update runs through the request's tenant-scoped client, which pins `Tenant.update` to the current tenant. The integration suite proves that a store's client asked to change another store's logo fails, leaves both stores unchanged, and deletes the file it uploaded for the attempt.

58. **Uploads are rate-limited to 20 per admin per 15 minutes.** Each upload spends a Blob operation from the monthly allowance, and the store pauses when that runs out. The limiter is the existing in-memory one, so it is per instance — enough to stop a stuck retry loop, not a determined attacker who already holds an admin session.

59. **The Vercel CLI's side effects were reverted.** `vercel blob create-store` overwrote the root `.env.local` (it held only a refreshable OIDC token) and re-appended a trailing `.env*` to `.gitignore` — reintroducing exactly the dead-negation bug fixed in #51. The line was removed; the local read-write token lives in `apps/zy-commerce/.env.local`, which is ignored.

60. **Two checks that were silently wrong now fail loudly.** The package's ESLint config linted its own `dist/` build output and lacked Node globals for the build script, so `pnpm lint` failed whenever `dist/` existed — invisible in CI only because CI lints before it builds. And the end-to-end smoke test still expected a "Demo Store" heading from before the Selkirk import; it now asserts what every storefront must show (a heading and the demonstration notice), plus that `/admin/settings` redirects a signed-out visitor to the login page.
